# Deploying Subtracker

```
Browser ──HTTPS──> Vercel (static React app)
                     │  /api/* rewritten (same site, so the session cookie stays first-party)
                     ▼
                   Render web service (Express API)  ──>  Neon Postgres (production branch)
                     ▲                                        │
GitHub Actions ──────┘ POST /api/internal/tick every 15 min   └─ Resend (email)
```

- **Frontend:** Vercel serves the built app and proxies `/api/*` to the API. The browser only ever
  talks to one site, so the cookie can stay `SameSite=Lax` and no CORS is needed.
- **API:** a single Render web service (`render.yaml`). Migrations run before each start.
- **Background work:** `.github/workflows/reminders.yml` calls the tick endpoint every 15 minutes,
  so no always-on worker is needed (decision D3 in `architecture.md`).
- **Database:** the Neon `production` branch. `dev` and `test` stay for development.

Any host that runs a long-lived Node process works for the API; Render is just the one described
here.

## 1. Database (Neon)

1. Get the production connection strings (pooled and direct):
   ```bash
   neon connection-string production --pooled
   neon connection-string production
   ```
2. The first deploy applies every migration from `0000_baseline`. A branch that already has tables
   from before the rebuild has to be emptied first (decision D1); otherwise the baseline migration
   fails on the existing tables.

## 2. Email (Resend)

1. Verify a domain you own in Resend (without one, Resend only delivers to your own address).
2. Create an API key with **sending access** only.
3. Pick a sender, e.g. `Subtracker <reminders@your-domain.com>`.

## 3. Google sign-in (optional)

1. In [Google Cloud Console](https://console.cloud.google.com/), create a project, then
   **APIs & Services → OAuth consent screen**: user type **External**, app name `Subtracker`,
   your support email. Scopes: just `openid` and `email`. Publish the app (or add yourself as a
   test user while it's in testing).
2. **Credentials → Create credentials → OAuth client ID**, type **Web application**:
   - Authorized redirect URIs: `https://<your-vercel-app>/api/auth/google/callback`
     (and `http://localhost:5173/api/auth/google/callback` for local development).
   - No JavaScript origins are needed: the browser never calls Google's APIs.
3. Copy the client ID and secret into `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` (Render, and
   `backend/.env` locally). Without them the button is hidden.

The redirect URI goes through Vercel on purpose: the callback sets the session cookie, and it
must be set on the app's own site.

## 4. API (Render)

1. In Render, create a **Blueprint** from this repository. It reads `render.yaml`.
2. Fill in the values marked `sync: false`:
   | Variable                                   | Value                                                            |
   | ------------------------------------------ | ---------------------------------------------------------------- |
   | `DATABASE_URL`                             | Neon **pooled** string (production)                              |
   | `DATABASE_URL_UNPOOLED`                    | Neon **direct** string (production), used for migrations         |
   | `APP_URL`                                  | the Vercel URL from step 5, e.g. `https://subtracker.vercel.app` |
   | `RESEND_API_KEY`, `EMAIL_FROM`             | from step 2                                                      |
   | `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | from step 3 (optional)                                           |
3. `CRON_SECRET` is generated by Render. Copy it for step 6.
4. Deploy, then check `https://<your-api>.onrender.com/api/health` returns `{"data":{"status":"ok",...}}`
   and `/api/docs` shows the API reference.

## 5. Frontend (Vercel)

1. In `frontend/vercel.json`, replace `REPLACE-WITH-YOUR-API-HOST.onrender.com` with the Render
   host, and commit.
2. Import the repository in Vercel with **Root Directory** `frontend` (framework: Vite). Vercel
   installs from the repo-root lockfile because the project uses npm workspaces.
3. Deploy. If the URL differs from what you put in `APP_URL`, update `APP_URL` on Render: it's used
   for links in emails and for the cross-site request check.

## 6. Scheduled reminders (GitHub Actions)

In the repository's **Settings → Secrets and variables → Actions**, add:

| Secret        | Value                                       |
| ------------- | ------------------------------------------- |
| `API_URL`     | the Render URL (direct, not through Vercel) |
| `CRON_SECRET` | the value Render generated                  |

Run the **Reminders** workflow once by hand (Actions → Reminders → Run workflow) and check it
succeeds.

## 7. Verify production

- Sign up with a real address, click the emailed link, and check you're logged in.
- If Google is configured, log out and use "Continue with Google" with the same address; it
  should land in the same account.
- Add a subscription; check the dashboard, calendar and forecast.
- Log out, use "Forgot your password?", reset, and log in with the new password.
- Export a CSV.
- Check the API's response headers include `Strict-Transport-Security` and that the session cookie
  is `Secure; HttpOnly; SameSite=Lax`.
- After the next reminders run, check the Render logs for a `Tick finished` line.

## Known trade-offs

- **Render's free tier sleeps** after about 15 minutes idle; the next request waits for a cold
  start. The 15-minute reminders run keeps it mostly awake. A paid instance removes this.
- **`TRUST_PROXY=2`** is right for traffic through Vercel. Someone calling the Render URL directly
  can forge the left part of `X-Forwarded-For` and spread their attempts across fake IPs. The
  per-email rate limit still applies to login and reset, so password guessing on one account stays
  limited. Restricting the Render service to Vercel's traffic would close this completely.
- **Neon scale-to-zero:** the database suspends after 5 minutes idle; the first query after that is
  a few hundred milliseconds slower.
- **Timezone rules** come from the deployed Node version's timezone database. Keep Node patched so
  daylight-saving changes (like British Columbia's) are picked up.
